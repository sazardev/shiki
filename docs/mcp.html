Agents & MCP

Your notes, as typed tools.

shiki-mcp is a real MCP (Model Context Protocol) server over stdio. It calls straight into shiki-core — the same domain logic as the TUI and CLI — never through the shiki binary, so an agent gets structured JSON arguments and results instead of shell quoting to parse. This page is the setup guide, the tool map and the safety model. 

shiki agent connect --all

Install

Every prebuilt archive and every package manager now bundles both binaries: shiki and shiki-mcp. AUR (shiki-bin or shiki), Scoop, Homebrew and the GitHub release tarballs/zip need nothing extra. Confirm the server is on your $PATH: 

shiki-mcp --version
shiki --version   # both should report the same version

Building from crates.io or a clone installs them separately — install both: 

cargo install shiki-cli shiki-mcp
# or, from a clone:
cargo install --path shiki-cli
cargo install --path shiki-mcp

If you ever see a version mismatch, update both together. shiki doctor flags the skew, and shiki agent status prints the resolved path and version.

Connect

One command writes the MCP entry into each client's own config and drops in usage guidance, so the agent knows to start with index, paginate, preview destructive edits with dry_run, and call sync_notebook after a batch of changes. 

shiki agent status                  # what is connected, where, and which shiki-mcp
shiki agent connect --all           # every supported client
shiki agent connect cursor          # or just one
shiki agent connect cursor --project  # this project's config instead of the user one
shiki agent connect generic         # print a snippet, write nothing
shiki agent disconnect --all        # reverse both halves

Each client defaults to its user/global scope (shiki notebooks aren't tied to one project), except Continue, whose MCP convention is project-only, and Codex, whose project config is only read for trusted projects — so Codex is user-scope only. --project switches to the current directory where the client supports it.

Every merge only touches the one key shiki owns (mcpServers.shiki, mcp.shiki, context_servers.shiki, or [mcp_servers.shiki]). If the existing file doesn't parse cleanly, nothing is written: the exact snippet to paste by hand is printed instead.

28 typed tools

Pagination and response shapes match the CLI exactly: limit/offset/ no_limit (default 50) and {total, offset, limit, returned, has_more, items}. A note is addressed by title or filename slug; every write tool defaults to general.default_notebook when notebook is omitted.

  • Read: list_notes, show_note, search_notes, query_notes, list_tasks, index, list_notebooks, diff_notebook, log_notebook, doctor.
  • Write: new_note, edit_note, delete_note, rename_note, move_note, tag_note, set_field, create_folder, delete_folder, move_folder, daily_note.
  • Git: sync_notebook (commit, and push when the notebook's policy allows it).
  • Notebook management: create_notebook, rename_notebook, delete_notebook, encrypt_notebook, decrypt_notebook, rekey_notebook.

Start with index to orient (counts, busiest folders/tags, never bodies or titles), then page through the specific list/search/query you need.

Safety model

  • Destructive calls need confirm: true. delete_note (trash-first, recoverable), delete_folder and delete_notebook (permanent) refuse without it — the tool-call equivalent of --yes.
  • dry_run: true previews the risky edits. rename_note reports the new path plus every note whose wikilinks would be rewritten; move_note/move_folder report source and destination; delete_folder/delete_notebook report the notes that would be destroyed. Dry runs need no confirm and touch nothing.
  • Writes are never auto-committed. new_note/edit_note and friends only write the file. sync_notebook is what commits (and pushes, if enabled); without it the changes sit as uncommitted working-tree state. The server instructions tell the agent this directly.
  • No hidden binary. Tools call shiki-core in-process, never shell out to shiki, so there is no CLI output to scrape or quote.
  • Read-only resources. Resources never write; prompts only gather context and ask the model to propose a plan.

Resources & prompts

Clients that support MCP resources can attach a note to a conversation without a tool call:

  • shiki://index — visible notebooks and note counts.
  • shiki://notebook/<name> — that notebook's notes (metadata only).
  • shiki://note/<notebook>/<path> — one note's full Markdown (frontmatter + body). Path segments are percent-encoded; the template is shiki://note/{notebook}/{path}.

Two prompts preload the relevant notes: weekly_review (open tasks plus recent daily notes) and inbox_triage (quick captures and untagged notes, with a proposed filing plan). Tools are universal; client support for resources/prompts varies (Zed, for example, supports prompts and tools but not resources). Clients that don't surface a resource can still read the same note with show_note.

Per-client notes

  • Gemini CLI reads GEMINI.md, not AGENTS.md — connect gemini writes its guidance there.
  • Zed calls MCP servers context_servers; the entry shape is the same command/args pair. Zed's settings are JSONC — if yours contains comments (or trailing commas) the merge refuses to rewrite it and prints the snippet to paste by hand instead of dropping your comments.
  • Codex uses TOML ([mcp_servers.shiki]). The merge preserves comments and sibling tables; project scope is intentionally unsupported.
  • VS Code uses the current Copilot harness config (mcpServers plus "type": "stdio") and a workspace .mcp.json. The older editor-managed .vscode/mcp.json format is deprecated and not written.
  • Continue gets a dedicated .continue/mcpServers/shiki.yaml rather than a merge into its own YAML.

Encrypted notebooks

An MCP server is spawned headless by its client and has no TTY, so there is nothing to prompt on. The server reads the passphrase from its own environment: 

SHIKI_PASSPHRASE="…"          # unlock decrypt/read/write
SHIKI_NEW_PASSPHRASE="…"      # new passphrase for encrypt/rekey

Set these in the environment the client launches the server with — for GUI clients that is often not your shell's environment, so check the client's own env block. Without it, encrypted tools fail with a clear message instead of hanging.

Troubleshooting

  • shiki-mcp: not found on PATH — install it (packages bundle it; otherwise cargo install shiki-mcp), then re-run agent connect so the absolute path is embedded. GUI clients often inherit a minimal $PATH.
  • Version mismatch — shiki doctor and agent status compare versions. Update both binaries together; the in-TUI updater only replaces the running shiki.
  • Client shows no tools — restart the client after connecting, and check that its config file is the one it reads (the table above).
  • Encrypted notebook errors — export SHIKI_PASSPHRASE in the server process's environment, not just your shell.
  • Agent made a mess — nothing is committed automatically. Use diff_notebook to inspect, git to revert, and next time ask for dry_run: true first.
  • Connect failed on an existing config — the file isn't clean JSON/TOML (for example a commented Zed settings.json) and was left untouched; paste the printed snippet in by hand.

More command-level detail lives in the CLI docs; the server's own tool descriptions are the source of truth for arguments.
